3 Motivation and Scope

3.1 Motivation

Describe the problem being addressed and why existing facilities are insufficient.

3.2 Scope

This proposal intentionally excludes unscoped enumerations from std::to_string overloads. It includes both scoped and unscoped enumerations in the std::formatter specialization on an opt-in basis.

Unscoped enumerations implicitly convert to their underlying integral types, meaning calls such as std::to_string(e) are already well-formed today and produce numeric output. Defining additional std::to_string overloads for unscoped enumerations would inevitably change the meaning of some existing code, violating the proposal’s status as a pure extension.

As scoped enumerations do not have this implicit conversion, calls like std::to_string(e) are not currently valid for them, and the proposed overloads support them unconditionally. However, programmers may have supplied their own std::formatter specializations for some enumeration types. To avoid potential conflicts with existing user-supplied formatting customizations, the proposed partial specialization restricts participation to enumerations annotated as formattable with one of the proposed annotations.

4 Impact on the Standard

This is a pure library extension.

This proposal does not require any changes in the core language. It does not alter the meaning or behavior of existing well-formed programs (save observability of new function overloads). It does not depend on any other library extensions; however, it would evolve to take advantage of the adoption of attribute reflection or changes to structural type requirements. It does account for and accommodate the eventual adoption of UTF-8 support in std::formatter.

This proposal introduces a new header, <annotations>, containing a new inline namespace, std::annotations. It further introduces the class template std::basic_formattable_with_default, the alias template std::formattable_with_default, and the annotation objects std::formattable and std::canonical therein. It also introduces the utility predicate std::is_enumerated_value in <utility>, a constrained partial specialization of std::formatter for annotated enumerations in <format>, and overloads of std::to_string for enumerable scoped enumerations in <string>.

5 Design Decisions

5.1 Overview

The core principle of the proposed design is to respect programmer intent, whether expressed or reasonably inferred. This sometimes means crafting a more complex structure behind a simple facade in order to facilitate that expression. C++ is a multi-paradigm language with a broad base of users and a rich history of trusting those individuals to decide what is best for their projects rather than forcing one-size-fits-all policy decisions. (See [D&E] section 4.2’s rule: “Don’t try to force people.”) The proposal also strives to maintain both backward and forward compatibility with the evolution of the Standard.

5.2.2.3 Format Specification Delimiter

After considering several characters to separate the enumeration-specific portion of the format specification from the portion for formatting the specified representation, this proposal chose to use the : (format-specifier separator) as the delimiter. This avoids introducing a different character into the format grammar and naturally extends the replacement field to give the appearance of a third section. This results in replacement fields that look like {:i:02X}, {:i}, {:i:}, {:}, or {::}.

5.2.3 Annotations

Annotations are vocabulary. Introduced in P3393R4?, they bring a new dimension in which code can communicate both with other code and with programmers. Absent standard terminology, everyone will invent their own, and like with natural languages, speakers of one dialect will not understand the slang of other dialects. Introducing sound annotations into the standard in an ergonomic way will have a large impact as the feature becomes widely used.

This paper proposes the introduction of the <annotations> header to contain standard annotations. This avoids needing to include <format> just to declare an enumeration, prevents the header proliferation that would ensue if every header had a corresponding <X_annotations>, and prefers the option that is easiest to teach. “Where is the annotation for …?” always has the same obvious answer.

Likewise, this paper defines its annotation types and objects in the proposed std::annotations inline namespace. The syntax for annotations becomes unwieldy with deeply nested names, so facilitating forms like [[=std::some_annotation]] and [[=some_annotation]] enhances developer ergonomics. The nested namespace, inspired by std::literals, allows users to access annotation names directly from std or use std::annotations to limit the names brought into their current scope.

While the annotations proposed here are designed to enable the proposed stringification and formatting facilities, they have been developed with broader use in mind. The author therefore invites feedback on the exact spelling of the annotation names to ensure they serve the wider ecosystem.

5.2.3.1 Designating Canonical Names

When selecting the enumerator name for a given value, one must sometimes select among a set of aliases all corresponding to the same value. At present, there is no mechanism to favor one over another, and there is no mechanism to recognize that one is [[deprecated]] in favor of another. This proposal introduces the std::annotations::canonical annotation to allow the designation of canonical enumerators inside their declaration. When an enumerator is annotated as canonical, its name is favored over unannotated enumerators with the same value.

5.2.3.2 Format Opt-In Annotations

Modeled on the pattern used throughout the STL, the proposed formatting opt-in annotation types specialize the class template std::annotations::basic_formattable_with_default. The char representation is thus exposed as the alias template std::annotations::formattable_with_default, and its default-constructed object is std::annotations::formattable. This leaves the door open for u8formattable_with_default, wformattable_with_default, et cetera as the need arises to provide per-type formatting defaults in additional contexts.

The basic_formattable_with_default template takes both the representation and format specifier character types as independent template parameters for maximum flexibility. This gives the committee slack as UTF-8 formatting support evolves because the formatting annotations can adapt to fit new proposals without substantial design changes. Class template argument deduction allows formattable_with_default (and any future aliases selecting different representation character types) to deduce its format specifier character type from its constructor argument.

5.2.3.3 User-Defined Formatting Annotations

namespace application {
    inline constexpr std::formattable_with_default hex_dword{"i:#10X"};

    struct layout_table {
        static constexpr std::formattable_with_default heading{"s:^20.20"};
        //...elided for brevity
    };

    enum class color24 [[=hex_dword]] {
        red   = 0xFF0000,
        green = 0x00FF00,
        blue  = 0x0000FF,
    };

    enum class cake [[=layout_table::heading]] {
        vanilla,
        chocolate,
        strawberry,
        butterscotch,
        sarsaparilla,
        pumpkin,
    };
} //namespace application

Because the formatter recognizes annotations by their type rather than by the name of the annotation object, users may define their own annotation objects of type std::formattable_with_default to establish reusable formatting conventions. These objects can be declared in user scopes and applied to enumeration types without requiring additional annotation types or special handling by the formatter. Such annotations establish defaults, which may still be overridden by the format specification at the call site.

5.3 Default Representation

The proposed formatter uses the string representation when unspecified by the caller and the annotation. Users directly formatting an enumeration with {} rather than converting it to its underlying integral type typically want to display its symbolic name. This is the primary reason for giving enumerations formatter support in the first place.

While it would be possible to infer intent and default to integer representation for enumeration types with no declared enumerators should the committee prefer it, that would complicate the interface and reduce usability in generic contexts. See Uniform vs. Inferred Default Representation.

5.4 Default Type-Qualification

This paper proposes a “smart default” type-qualification where the default depends on the specified representation and whether the value corresponds to a named enumerator. As the name of an enumerator often carries sufficient context for a familiar user to identify its probable type, the default in this case is unqualified. For values without a named enumerator, the default for the string representation treats the value as a type-qualified pseudo-enumerator because the numeric value alone carries no context. These defaults apply to both the std::formatter and to std::to_string. When the specified format representation is the underlying integral type, the default is an unqualified number, trusting the caller to provide appropriate context (or to specify a type-qualified format if desired).

5.5 Non-Enumerable Types

The std::to_string overloads are constrained to require enumerable scoped enumerations, so calls will fail to compile. The std::formatter specialization, on the other hand, rejects non-enumerable types during format-string parsing, at the moment the caller specifies representing the value as an enumerator name string. Instantiation of the std::formatter or annotation of an enumeration is permitted because it is perfectly reasonable for a programmer to format an enumeration value as a number or format the enumeration type name without the type being enumerable.

5.6 Constraints and Limitations

5.6.1 Reflecting on Attributes

Should [P3385R8] be adopted into the Working Draft, this proposal would use its facilities to favor non-deprecated enumerator names over deprecated names.

5.6.2 Structural Types

Should [P4414R0] be adopted into the Working Draft, this proposal would modify the proposed definition of std::basic_formattable_with_default to encapsulate a std::basic_string_view rather than storing public non-static data members. These data members are currently unspecified with the intent that implementations could plausibly replace them without breaking the binary representation of the annotation objects if the standard were to permit it in the future. The revised definition would also employ the structural class-property-specifier to allow real encapsulation.

5.6.3 UTF-8 Support in std::formatter

This proposal does not extend std::formatter to support formatting UTF-8 strings or character types directly. If support such as that proposed in [P3258R0] were to be adopted, the mechanism proposed here could be extended to connect that facility with std::meta::u8identifier_of by means of a std::u8formattable_with_default type alias.

This paper also does not propose to extend std::formatter to support UTF-8 characters in format strings. If support were to be adopted, the mechanism proposed here would automatically interoperate through its character type template parameters that accept char8_t arguments.

5.7 Alternatives Considered

5.7.1 Unified Syntax vs. Separate Annotations

[P4267R1] proposes std::format_as_identifier and std::format_as_underlying as separate annotations. This requires enumeration type authors to select the representation of their enumeration types at the point of declaration and prevents users of those types from overriding that choice at their call sites.

This paper, instead, provides a unified format specification syntax to defer the choice of representation to the caller and a single format annotation type which still allows the creator of the type to select a per-type default.

Should the committee prefer the syntax of discrete named annotation objects like std::format_as_identifier and std::format_as_underlying, they could be implemented under this proposal:

inline constexpr formattable_with_default format_as_identifier{"s"};
inline constexpr formattable_with_default format_as_underlying{"i"};

The user would retain the ability to override the representation at the call site.

As a practical matter, should a developer wish to enforce their choice of formatting representation on users, the only way within the std::format framework is to explicitly specialize std::formatter for the type. An annotation-based facility cannot enforce such a choice, as users remain free to explicitly specialize std::formatter for the type and format it as they wish.

5.7.2 Annotation Class Template vs. Separate Annotation Types

The initial draft of the reference implementation had formattable_with_default and formattable annotations. When considering how to be forward compatible with UTF-8 formatting, the obvious solution was u8formattable_with_default and u8formattable. This works, but the definitions of the two classes are, aside from identifier names, identical. In addition to duplicating the definitions, the formatter specialization had to replicate its annotation detection for both annotation types. The straightforward solution was to make the representation character type a template parameter that distinguishes the representation families and unify the definitions into a single class template. When exploring options for supporting non-char-based format specification strings, adding the format specification character type as a template parameter and connecting it with the character type of the std::formatter made that support relatively simple.

Thus, this paper relies on std::annotations::basic_formattable_with_default<typename RepresentationCharT, typename FormatSpecifierCharT> to build an extensible mechanism capable of supporting future char8_t formatting. It further provides std::annotations::formattable_with_default<typename CharT> as a user-facing alias for std::annotations::basic_formattable_with_default<char, CharT> and holds space for std::annotations::u8formattable_with_default<typename CharT> as the corresponding alias for std::annotations::basic_formattable_with_default<char8_t, CharT>. The annotation object std::annotations::formattable (like the as-yet-unproposed std::annotations::u8formattable) simplifies the case where no default format specification is provided. Because the constructor of std::annotations::basic_formattable_with_default takes a reference to an array of FormatSpecifierCharT, CTAD correctly deduces [[=formattable_with_default("i")]] as std::annotations::basic_formattable_with_default<char, char> (assuming the relevant using directive/declaration). This provides the best of both worlds: clean annotation syntax, a unified annotation family, and a clear path for extension.

5.7.3 Uniform vs. Inferred Default Representation

An alternative design would infer the default representation from whether the enumeration declares any enumerators: using string representation (s) when at least one enumerator is declared, and falling back to integer representation (i) when the enumerator list is empty.

This inferred approach has practical appeal for enumerations used purely as strong integer aliases (such as enum class user_id : std::uint64_t {};). Because an enumeration with no declared enumerators can never produce an enumerator identifier—every value is unenumerated—authors annotating such a type with [[=std::formattable]] may frequently want bare numeric output rather than type-qualified pseudo-enumerators (such as user_id::42).

However, a uniform string default is preferable for three reasons:

  • Predictability and generic programming: A single rule—{} always defaults to string representation unless overridden by formattable_with_default or the call-site format specification—is trivial to teach and reason about. Under an inferred rule, generic code cannot know an unannotated enumeration’s default representation without inspecting its enumerators (for example, via a has_named_enumerators helper).
  • Evolution stability: Under an inferred rule, adding a sentinel enumerator (such as invalid = 0 or none = 0) to a previously empty enumeration would silently change the default representation from integer to string. Worse, any existing call site relying on that inferred integer default with numeric format specifiers—such as {:#010b}—would suddenly fail to compile, because # and 0 are invalid in string format specifications.
  • Explicit intent for strong types: Enumerations without enumerators are typically introduced specifically to distinguish a domain type from a raw integer. Producing a type-qualified pseudo-enumerator by default preserves that distinction, while [[=std::formattable_with_default("i")]] gives authors a concise, explicit way to opt into bare integer formatting when desired.

5.7.4 Accessing the Annotated Default Format Specification

The syntax for accessing the default format specification stored by a std::basic_formattable_with_default object could take practically infinite forms. Directly accessing the pointer stored by the constructor would work, but it would be preferable to avoid exposing a raw pointer or a public data member. After considering many member function names such as get, value, as_string, get_string_view, as_string_view, get_basic_string_view, as_basic_string_view, a pattern appeared. This operation requires converting the stored representation into a type-safe view of the characters stored by the annotation, which is idiomatically spelled operator std::basic_string_view for the stored character type. Using the conversion operator provides a clean interface that does not require selecting a name. Furthermore, should another type such as an explicit std::string copy be desired in the future, the door is open to extension.

5.7.6 String Representation of Unenumerated Values

enum class rgb_color : std::uint32_t {
    red   = 0xFF0000,
    green = 0x00FF00,
    blue  = 0x0000FF,
};

auto black     = rgb_color{0x000000};
auto black_str = std::to_string(black);

Considering this basic scoped enumeration representing RGB colors, what should be the string representation of an unnamed color? Since named enumerators are written rgb_color::red, rgb_color::green, and rgb_color::blue, this proposal uses a parallel syntax for unenumerated values and produces rgb_color::0, treating the underlying value as a pseudo-enumerator. This preserves the enumeration type and underlying value for debugging/logging purposes. Other candidate representations discard some of this information or treat unenumerated values as construction expressions that are less readily parsed by consumers. The proposed representation also avoids favoring either parenthesized or braced initialization syntax, each of which has its own stylistic advocates and semantic distinctions in C++.

Status

Should the programmer desire either of the last two options, the is_enumerated_value utility function proposed here provides that functionality:

Fallback to Pure Value
Fixed Fallback 
if (!is_enumerated_value(black)) {
    black_str = std::to_string(
        std::to_underlying(black)
    );
}
 
if (!is_enumerated_value(black)) {
    black_str = std::string{"<UNNAMED>"};
}

5.7.7 Format Specifiers

5.7.8 Rejecting Non-Enumerable Types at formatter Instantiation

The std::formatter specialization could be constrained to require enumerable enumerations, matching std::to_string. This paper finds that approach unacceptable because std::formatter supports formatting modes (i.e., the underlying numeric value and the enumeration type name) that do not depend on enumerator names and remain valid for non-enumerable types. The chosen design follows the [D&E] principle that C++ rejects actual errors rather than potential errors.
